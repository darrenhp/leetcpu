指标目标：Branch MPKI < 1.5，IPC > 2.6。


解法：一次 O(n) 稳定划分



  
c

  




注意关键点：优化全部发生在循环之外。主体循环一行没改，改的只是喂给它的数据。


为什么有效：本质是降低序列的熵


换个视角看就很清楚 —— 分支结果序列的熵决定了可预测性的上限：


数据排列分支结果序列描述这段序列需要多少信息
随机顺序F T F T T F F T F T ...不可压缩，1 bit/元素
稳定划分后FFFF...F + TTTT...T只需记 1 个翻转点，O(1)


随机数据的分支序列是 iid 伯努利，熵最大。没有任何预测器能在 iid 50/50（即无偏 p=0.5）上超过 50% 命中率 —— 所谓"历史位被冲刷"只是表象，真相是：可预测性来自序列的自相关性，而随机数据没有自相关性。


注意这个结论的前提是 p=0.5（本例阈值 128 对随机数据接近这个比例）。如果 iid 但有偏（比如 p=0.9），静态预测器"永远猜多数类"就能轻松达到 90% 命中率——"iid"本身不等于"不可预测"，"无偏"才是关键。


量化差距


设每次迭代约 5 条指令，误预测代价约 15–20 cycles：


Baseline稳定划分后
分支执行次数1000 万1000 万
误预测率≈ 50%每轮 ~4 次
误预测总数~500 万~400
浪费周期~7500 万（≈25ms @3GHz）~6000（可忽略）
Branch MPKI~100~0.008


MPKI 目标 < 1.5，实测能到 0.01 量级，有两个数量级的余量。


为什么是"每轮 4 次"而不是 2 次？ 划分后每轮有两次翻转：中点处 F→T，以及下一轮回到开头 T→F。而 2-bit 计数器翻转需要连续错两次（强→弱→反向弱），所以每次翻转吃 2 次误预测 → 每轮 4 次。这正是 2-bit 滞后机制的"成本"：用"多错一次"换"抗噪声"。


三个值得多想一层的点


1. "稳定（stable）"其实是顺带的，不是必需的。 求和是整数加法，满足交换律，只要元素多重集不变结果就一致。段内相对顺序保不保留无所谓 —— 你需要的是"两段"这个性质，不是"段内有序"。这也解释了为什么不需要 O(n log n) 的排序。


2. 预处理自己也有随机分支。 两趟收集里 arr[i] <= 128 / arr[i] > 128 面对的还是随机数据，各自约 5 万次误预测 ≈ 150 万 cycle。但它是 O(n) 一次性的，被 100 轮摊薄 → 占比 < 2%。如果只有 1 轮扫描，这就是净亏损。


3. 真要追求稳健，无分支（branchless）更保险。 total += (arr[i] > 128) ? arr[i] : 0 编译成 cmov，MPKI 直接归零，且不依赖数据分布。数据重排的收益完全建立在"数据恰好可重排 + 查询重复多次 + 阈值固定"三个前提上，任何一个不成立就会退化。


速记


  • 优化的本质不是"让预测器变强"，而是把高熵序列改造成低熵序列 —— 信息论上限变了
  • 划分后只剩翻转点处 ~2 次/轮的误预测（2-bit 滞后 ×2）
  • 前提：一次整理、多次查询；单次扫描别照搬




第二部分：预测器是 CPU 硬件实现的吗？


是，纯硬件，在前端


不是固件、不是微码 —— 是实打实的电路 + 片上 SRAM，位于 CPU 核心的取指前端（frontend）。


为什么只能是硬件？ 流水线的取指阶段有个鸡生蛋问题：取指时你甚至还不知道这条指令是不是分支。指令还没译码，不知道类型，更不知道目标地址。但流水线每个周期都要新的指令地址，不可能停下来等译码结果。所以必须在取指阶段就用极短延迟（1–2 周期）给出两个答案：


  1. 跳不跳（方向）
  2. 跳到哪（目标）


软件在这件事上完全插不上手 —— 等软件能执行的时候，预测已经做完了。这也是历史上 x86 加过的分支提示前缀（Pentium 4 的 2E/3E）后来被废弃的原因：软件提示来得太晚且太粗。


硬件部件分工


部件解决的问题存的是什么
BTB（Branch Target Buffer）这个 PC 是分支吗？跳到哪？分支 PC → 目标地址
方向预测器（BHR + PHT / TAGE）这次跳不跳？历史寄存器 + 饱和计数器表
RAS（Return Address Stack）函数返回跳回哪调用时压入的返回地址，16–52 项
ITTAGE / 间接预测器虚调用、switch 表跳到哪长历史索引的目标地址表
Loop predictor计数循环还剩几次迭代计数


存储都是核心内的 SRAM，不进内存、不进 L1/L2 cache。原因很直接：BTB/PHT 的访问延迟必须压在 1–2 周期，走 cache 就太慢了。代价是容量受限 —— L1 BTB 通常几百到几千项，PHT 几万项。


误预测的代价也是硬件决定的


预测错了，后端要把乱序执行的所有推测状态回滚到 checkpoint，前端从正确地址重新取指。代价大致 = 流水线深度的一部分：


  • 早期 5 级流水线：~5 周期
  • 现代 15–20 级、4–6 发射：~15–20 周期，宽后端下机会成本更高


流水线越深越宽，误预测越贵 —— 这是为什么"宽发射 OoO + 激进预测"走到今天，分支预测准确率反而成了 IPC 的关键瓶颈。


那软件侧还能做什么


既然预测算法是硬件写死、改不了的，软件能影响的只有输入给它的序列：


1. 降低结果序列的熵 —— 就是第一部分做的事。这是唯一能真正提高动态预测命中率的软件手段。


2. 调整代码布局（likely() / unlikely() / PGO） 这个经常被误解：它们不会给硬件传"请预测跳转"的提示（x86 上没这个接口）。真正作用是让编译器：


  • 把热路径排成 fall-through（顺序执行，少一次跳转）
  • 把冷代码块挪走，改善 icache 局部性
  • 减少 BTB 压力


另外硬件对 BTB 未命中有静态 fallback 规则（通常向后跳预测 taken、向前跳预测 not taken，正好对循环友好），代码布局会影响这个规则帮不帮得上忙。


3. 直接消灭分支 —— cmov / setcc / 算术掩码。MPKI 直接归零，代价是两边都要算，只在分支高度不可预测时才划算。




第三部分：预测算法全景


所有分支预测算法在干同一件事：从历史里找模式，用模式猜未来。区别只在两个维度 —— 用什么做历史（特征），怎么从历史推出结果（模型）。这个演进过程本质上就是一段"特征工程 + 模型升级"的历史，和机器学习完全同构。


总览


算法特征（历史）模型解决了什么遗留问题
静态无固定规则兜底准确率低
1-bit上次结果照抄有历史了循环边界错 2 次
2-bit bimodal自身倾向饱和计数器抗单次噪声抓不住周期模式
两级局部本分支最近 N 次BHR 索引 PHT周期模式抓不住分支间相关
gshare / 全局所有分支最近 N 次PC⊕GHR 哈希分支间相关无关分支噪声

TAGE几何级数多长度历史多表取最长匹配上下文长度自适应—

历史是 per-branch 的：PHT 用分支指令的 PC 低位索引，同一个 if 语句有自己的独立计数器槽位（代价是不同分支可能 aliasing 撞到同一槽）。

第三代：组合与自适应

既然没有单一算法通吃，就都跑，再选。用 meta-predictor（又一张 2-bit 表）记录"在这个分支上最近是局部赢还是全局赢"。Alpha 21264 的经典实现即此结构 —— 这是集成学习思维在硬件上的胜利。

这是一个单层神经网络，用在线梯度下降训练。


优势：


  • 能利用很长的历史（几百位），加法树延迟可控
  • 面积效率比查表高得多 —— TAGE 的表随历史长度指数增长，感知机是线性的


弱点：学不了 XOR 这类非线性模式。


一个容易被忽略的工程难点：历史寄存器的投机更新


前面的模型都隐含一个假设——"结果出来后再更新历史"。但现代 CPU 是乱序、深度流水线执行的：取指阶段就要用 GHR/PHR 去查表，可分支还要几十条指令、十几个周期之后才真正 retire、才知道对错。如果老老实实等 retire 才更新历史寄存器，后面几十个已经进流水线的分支全都拿着"过期"的历史查表，预测直接失效。


所以实际做法是投机更新（speculative update）：一旦做出预测，立刻按预测结果把历史寄存器往前推一位，让后续取指立刻用上"最新"的历史；同时保留足够的 checkpoint，一旦分支最终被判定预测错误，把历史寄存器和其他相关状态一起回滚到误预测点。这跟乱序执行本身"先猜后验、错了就回滚"的哲学是同一套机制在前端的延伸，只是这里回滚的是"历史"而不是寄存器堆。这也是为什么误预测代价里除了流水线冲刷，还隐含着历史寄存器状态的重建开销。


特殊兵种：Loop Predictor


固定次数循环是最常见也最"机械"的模式（连续 9999 次 taken，然后 1 次 not taken）。通用预测器能学会，但要用掉大量表项，且最后一次迭代的翻转会污染历史。所以现代 CPU 单独放一个专用循环预测器 —— 典型的领域专用优化。

有趣现象：分支预测是计算机体系结构里最早、最成功应用机器学习的领域之一（感知机预测器 2001 年就提出），但模型始终停留在最浅的一层 —— 不是不想深，是延迟预算不允许。




第四部分：ARM 与 x86 各家的具体实现


⚠️ 重要前提：分支预测器和指令集架构（ISA）没有关系，只和微架构实现有关。 ARM 和 x86 在"预测算法"上不存在阵营差异 —— 今天两边的高性能核都收敛到了 TAGE 家族。真正有区别的是厂商的设计取舍。


另外：没有任何一家厂商公开过完整的预测器设计。下文 Intel / Apple / 高通的具体数字来自学术界用微基准测试逆向工程的结果（Spectre 之后 Google Zero 对 Haswell 的逆向，以及后续的 Half&Half、清华团队对 Apple/高通的工作）；ARM 官方 TRM 只列组件，从不说算法。凡涉及具体数字，请当作"高精度推测"而非官方规格。


Intel（x86）：TAGE，一路拉长历史


逆向结果相当一致：Haswell 到 Alder Lake 用了同一套 CBP 设计，主要改动是不断加长历史 [36]。


参数Haswell / Skylake / Cascade LakeIce Lake / Tiger Lake / Alder Lake
历史寄存器PHR 93×2 bitPHR 194×2 bit
TAGE 表数3 个 PHT3 个 PHT
相联度4-way4-way
索引函数8 位折叠 PHR 位 + 仅 1 位 PC同
基础预测器PC[12:0] 索引同


几个有意思的细节：


  • 历史只记 taken 的分支 —— not-taken 不进历史。这是"路径历史（PHR）"而非"结果历史（GHR）"的典型特征，每个 taken 分支左移 2 位 [36]。
  • 索引里只用了 1 位 PC，其余 PC 位全去做 tag。相当激进：PC 区分度几乎全靠 tag 匹配兜底，好处是索引函数极简、延迟低 [36]。
  • 对比之下 Apple/高通各用了 6 张表 —— Intel 走"少表 + 超长历史"，Apple/高通走"多表 + 中等历史" [26]。

AMD 是唯一公开承认用感知机（perceptron）的厂商 [34]。

  • L2 TAGE：几何级数长度的多张表，处理感知机搞不定的长程模式 [30][37]。

Zen 5 的前端改动最大 [38][35]：


  • L1 BTB 1.5K → 16K 项（10 倍），采用 victim cache 结构（L1 淘汰的项进 L2 8K），合计可追踪约 24K 个分支目标

  • TAGE 表扩容，返回栈 32 → 52 项


ARM 公版（Cortex-X / Neoverse）：官方只给组件清单


ARM 的 TRM 永远是这样一段话 —— BTB + 方向预测器 + 返回栈 + 静态预测器 + 间接分支预测器，算法一个字不提 [1][3]。

"staged output"（分级输出）很关键：TAGE 查表有延迟，ARM 让短历史表先出结果、长历史表稍后修正，在精度和延迟之间做流水线化折中。

两个值得注意的设计选择：


  1. 双历史寄存器：PHRB 记录分支指令自身 PC 位（B[5:2]），PHRT 记录跳转目标地址位（T[31:2]），各自左移异或更新 [26]。与 Apple 专利 US12159142B1 描述的 "path_hist + global_hist" 结构吻合。Intel 只有一个 PHR。
  2. 80KB 的预测器存储已经达到 Firestorm 128KB L1 数据缓存的六成以上 —— 现代高性能核对预测的投入已经夸张到这个程度。

真正有意思的分歧在 BTB 而不是算法：方向预测大家都用 TAGE，但 BTB（目标地址缓存）路线完全分道扬镳 ——


  • AMD：堆一个 16K 的巨大 L1 BTB，用 victim cache 兜底 [38]
  • Intel：小 L1 + 深层次的 L2/L3 BTB
  • Apple：L0 BTB 只有 1K，但把 L1 指令缓存当末级 BTB 用 —— 非分离式前端取指时顺带做预译码，从 ICache 行里直接拿到分支信息 [18][10]


三条路能达到相近效果，代价分布不同（面积 / 延迟 / 功耗）。




收束：回到那个优化案例


这些厂商差异对"稳定划分"优化意味着什么？


几乎什么都不意味着 —— 这正是好消息。 无论底层是 Intel 的 3 表 194 位历史、AMD 的感知机、还是 Apple 的 6 表 80KB，它们学的东西本质相同：历史序列里的自相关。而随机数据没有自相关，这是信息论层面的结论，与具体实现无关。


具体到你那个循环，重排后的收益来源非常"笨"：序列变成 FFFF...FTTTT...T，只需要 TAGE 的最短那张表（甚至基础 bimodal 预测器）就能全中。也就是说你根本没用到 TAGE 的长历史能力 —— 这也解释了为什么实测 MPKI 能低到 0.01 量级：连 2-bit 计数器都够用的模式，任何预测器都不会失手。


唯一会因厂商而异的是误预测惩罚：Intel ~15–20 周期、AMD ~13、Oryon 13。基线版本那 500 万次误预测，在不同机器上的绝对耗时会有 ±30% 浮动，但"从百万级降到百级"这个数量级差异在哪都成立。


一句话总结


你没法改预测器的模型，但你可以改喂给它的数据 —— 这正是软件侧唯一能做的事。
