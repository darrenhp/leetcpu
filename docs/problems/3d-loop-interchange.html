三维数组：修正循环顺序

把最快变化的一维放到最内层 —— 步長从 16KB 降到 4 字节。

原始英文标题：3D Array — Fix Loop Order for Sequential Access

题面

对 64×64×64 的整数数组求和。数组按行优先存储：元素 [i][j][k] 位于偏移 i*64*64 + j*64 + k。

当 k 在最内层变化时，相邻访问在内存中彼此相邻 —— 一条缓存行可覆盖 16 个整数。

基线却把 i 放在最内层，于是每步跳跃 64×64 = 4096 个整数（16KB），每次访问都要拉一条新的缓存行。

任务
实现 long solve(int *arr, int n)，返回以行优先存于 arr 的 n×n×n 个整数之和，且最内层循环遍历最后一个维度 k。

约束

  • n = 64（固定，数组为 n×n×n = 262144 个 int）
  • arr 行优先：元素 [i][j][k] 位于 arr[i*n*n + j*n + k]
  • 不允许多线程
  • 结果必须精确

示例

输入64×64×64 行优先 int 数组（共 1MB）
输出全部元素之和
说明仅交换循环顺序即可：数组总量 1MB 虽超出 L1，但顺序扫描能 100% 利用每条缓存行，且硬件预取器可以完美工作。

优化报告


维度内容


核心瓶颈循环顺序导致的跨步访问


一句话思路把最快变化的一维放到最内层 —— 步長从 16KB 降到 4 字节。


报告摘要纯循环交换：把 for k / for j / for i 改成 for i / for j / for k，让最内层沿内存中连续的方向推进。





瓶颈定位
基线最内层 sum += arr[i*n*n + j*n + k]，i 变化时地址跳 n*n*4 = 16384 字节。
整个数组 1MB，远大于 L1；跨步 16KB 意味着每条缓存行只用 4 字节，有效率 1/16。
更糟的是：16KB 的固定跨步超出多数硬件预取器的识别范围，预取器完全帮不上忙。
优化思路
行优先数组中，最后一维（k）在内存中连续。让 k 成为最内层循环变量，相邻迭代地址只差 4 字节。
这样每条 64 字节缓存行被连续使用 16 次，利用率 100%。
顺序流式访问还能被硬件 stride 预取器完美预测，进一步掩盖剩余延迟。
关键改动
三重循环顺序由 k→j→i 改为 i→j→k（循环体完全不变）。
求和满足交换律，因此改变遍历顺序不影响结果。
索引表达式 i*n*n + j*n + k 保持不变 —— 编译后内层实际是 base++ 的顺序扫描。
为什么更快
缓存行利用率从 4/64 提升到 64/64，等效访存量降为 1/16。
L1 MPKI 从数十降到个位数，硬件预取器开始生效。
这是最经典的"零成本优化"：不改数据结构、不改算法，只调整循环嵌套顺序。
常见误区
以为编译器会自动做循环交换：C 编译器通常不敢擅自改变浮点求和顺序；对整数虽可能，但依赖别名分析，不能指望。
混淆行优先与列优先：Fortran/NumPy 默认列优先，此时最快变化的是第一维，方向恰好相反。
忽略 TLB：跨步 16KB 也会在页面之间跳跃，进一步加剧 TLB 压力。



要点速记
  • 循环交换让内层连续访问
  • 缓存行利用率提升 16 倍
  • 零成本改动


常见误区与边界条件
  • 行/列优先语言差异
  • 不要指望编译器自动交换
