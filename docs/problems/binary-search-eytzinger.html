二分查找：Eytzinger 布局 + 预取

把 O(log N) 次串行失效，变成按层批发的并行失效。

原始英文标题：Binary Search — Cache-Friendly Eytzinger Layout

题面

在含 65,536 个键的有序数组中查找 100,000 个查询值。标准二分查找每次查询要触碰 O(log₂N) ≈ 16 条缓存行，每层一条。

每次失效都是串行的 —— 在当前的比较得出结果之前，下一个地址是未知的。

10 万次查询就是约 160 万次串行依赖的缓存失效。Eytzinger 布局以 BFS 顺序存储查找树：根在下标 1，其子节点在 2 和 3……

任务
实现 int solve(const int *keys, int n, const int *queries, int q)，返回在键集合中被命中的查询数量。允许在查找前内部重排 keys。

约束

  • keys[] 升序且含 n 个互异值（≤65536）
  • q = 100000 次查询
  • 返回精确的命中计数
  • 不允许多线程
  • 允许并鼓励使用 __builtin_prefetch

示例

输入keys = 65,536 个有序 int；queries = 100,000 个查询值
输出命中的查询个数

优化报告


维度内容


核心瓶颈串行依赖的缓存失效


一句话思路把 O(log N) 次串行失效，变成按层批发的并行失效。


报告摘要两招并用：①把数组重排为 Eytzinger（BFS）布局，使查找可以用 k = 2k + (eyt[k] < x) 无分支推进；②在处理第 k 层时用 __builtin_prefetch(&eyt[4*k]) 一次性把未来若干层的节点批量取入缓存。





瓶颈定位
标准二分查找的每一步地址都依赖上一步的比较结果 —— 16 次完全串行的缓存失效。
10 万次查询 × 16 层 ≈ 160 万次串行失效，每次约 200 周期，总计数亿周期的纯等待。
此外 lo/hi 两条分支各自都难以预测，进一步加剧前端开销。
优化思路
Eytzinger 布局：把有序数组按"二分查找树"的 BFS 顺序重排，根在下标 1，左右孩子在 2k 与 2k+1。
于是查找可以写成无分支形式：k = 2*k + (eyt[k] < target) —— 只需一条 setl/比较指令，没有跳转。
层间预取：第 k 层的节点下标都落在 [2^k, 2^(k+1))，而 4*k 恰好指向第 k+2 层的区域。在处理第 k 层时预取 eyt[4*k]，就能提前两层发起请求，让多层失效重叠。
关键改动
递归 build() 以中序遍历有序数组，把中位数放在 eyt[node]，左右半区递归到 2*node 与 2*node+1。
查找循环：while (k <= n) { __builtin_prefetch(&eyt[4*k], 0, 0); if (eyt[k] == target) {...} k = 2*k + (eyt[k] < target); }
用 calloc(n+2, ...) 分配，保证越界位置为 0，循环条件 k <= n 即可自然终止。
为什么更快
无分支推进消除了分支预测失败，也让查找路径不再因误预测而被清空。
层间预取让相距两层的节点并行取入，把 16 次串行失效压缩成约 16/2 次批量失效。
BFS 布局的额外好处：树的顶部几层体积极小（前 4 层只有 15 个节点），几乎永远驻留 L1，因此前几次比较基本不失效。
常见误区
只做 Eytzinger 不做预取：无分支推进能减少前端开销，但串行失效依然存在，收益有限。
预取 2*k 而非 4*k：预取下一层来不及掩盖 200 周期延迟，必须跳两层以上。
忽略构建成本：重排是 O(n)，只有在查询次数远大于键数量时才划算（本题 10 万查询 vs 6.5 万键，处于临界，实际收益依赖查询量）。



要点速记
  • BFS 布局支持无分支推进
  • 按层批发预取打破串行
  • 树顶层天然驻留 L1


常见误区与边界条件
  • 只改布局不预取收益有限
  • 构建成本需被查询量摊薄
