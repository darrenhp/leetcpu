聚集重排：按页聚簇访问

用计数排序把随机索引按页分组，让访存在物理页上聚集。

原始英文标题：Gather Reordering — Cluster Accesses by Cache Region

题面

用一组索引置换从一个大数组中求和。基线按到达顺序遍历置换，于是每次迭代都可能跳到数据数组的完全不同的区域。

数据数组 512KB、索引随机散布，多数访问落在冷缓存行上，CPU 几乎每次迭代都在等内存。

请在内部对访问重排，让指向同一区域的索引彼此靠近，然后再执行聚集。

任务
实现 long solve(const int *data, const int *indices, int n)，精确返回所有 data[indices[i]] 之和，同时通过在聚集前重新分组访问来改善缓存局部性。

约束

  • n = 131072（评测中固定）
  • indices[] 是 0..n-1 的一个置换
  • 每个被引用元素必须恰好访问一次
  • 不允许多线程
  • 结果必须精确

示例

输入data = 512KB int 数组；indices = 随机置换
输出全部被引用元素之和
说明求和与顺序无关，因此可以自由重排访问顺序 —— 这正是本题留给你的优化空间。

优化报告


维度内容


核心瓶颈页级（TLB）与缓存局部性


一句话思路用计数排序把随机索引按页分组，让访存在物理页上聚集。


报告摘要用计数排序（三趟：统计、前缀和、散布）把索引按所属 4KB 页重新分组，然后按新顺序顺序聚集。访问于是从"全数组随机跳"变成"逐页顺序扫"。





瓶颈定位
512KB 数据在 4KB 页下跨越 128 个页面；随机访问意味着每次迭代都可能换页。
结果是双重的：缓存行冷（L1 未命中）且 TLB 条目被反复冲刷（页表遍历开销叠加在缓存访问之上）。
单纯预取对此帮助有限 —— 因为访问顺序本身就是发散的。
优化思路
求和满足交换律，访问顺序可以自由改变。
按页分组：page = index / 1024（4096 字节 / 4 字节）。用计数排序把同页的索引聚到一起。
重排后，聚集阶段在一段时间内只访问同一个 4KB 页内的地址 —— 该页的 TLB 条目与缓存行都能被充分利用。
关键改动
第一趟：统计每个页包含多少个索引 counts[indices[i] / 1024]++。
第二趟：前缀和得到每页在输出数组中的起始偏移 offsets[]。
第三趟：散布 ordered[offsets[page]++] = indices[i]。
注意实现细节：散布后 offsets 已被推进，需要再后移一格还原，才能正确表达每页起始位置（参考实现中用了倒序 shift 的技巧）。
最后按 ordered 顺序做一次完全顺序的聚集。
为什么更快
页级局部性：同一页的约 1024 个索引被连续处理，TLB 只需一次装填即可服务上千次访问。
缓存局部性：页内 4KB 恰好是 L1 可容纳的量级，页内访问能反复命中。
代价是三趟 O(n) 预处理与 O(n) 额外内存 —— 相比 13 万次随机访存的节省，完全值得。
常见误区
以为要按缓存行（64B）分组：过细的分组会让分组本身开销过大；按页分组在 TLB 收益与开销之间取得平衡。
忘记还原 offsets：散布循环中 offsets[page]++ 修改了数组，若直接复用会导致后续逻辑错位。
忽略额外内存：需要 counts、offsets、ordered 三个数组，内存紧张时需评估。



要点速记
  • 计数排序按页聚簇
  • 同时改善 TLB 与缓存局部性
  • 三趟 O(n) 预处理的代价可控


常见误区与边界条件
  • offsets 被推进后需还原
  • 分组粒度需权衡
