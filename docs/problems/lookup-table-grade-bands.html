22 简单 分支预测 分支预测 · ChampSim · TAGE-SC-L · branch study

等级分档：用查表替代嵌套分支

分值只有 0–100 —— 那就把 101 种结果预先算好。

原始英文标题：Grade Bands — Replace Nested Branches with a LUT

题面

在大量重复轮次中把分数归类到等级区间。基线对每一轮的每一个分数都走一遍嵌套 if/else 树。

当分数在输入范围内广泛分布时，控制流的可预测性远不如它应有的水平。

请预计算一张很小的查找表，然后把热循环简化为一次查表与累加。

任务
实现 long solve(const unsigned char *scores, int n)，返回 200 轮的加权总和，其中分数按等级区间映射为权重。

约束

  • n = 100000（评测中固定）
  • scores[i] 取值范围 0..100
  • 允许预计算查找表
  • 不允许多线程
  • 结果必须精确

示例

输入scores = 100,000 个 0–100 的分数
输出200 轮的加权总和（<60→1，<70→2，<80→4，<90→8，否则 16）
说明分数只有 101 种可能取值，却要被判断 200×100,000 = 2000 万次 —— 典型的"重复计算同样结果"。

指标目标含义
IPC> 2.8每周期退休指令数
Branch MPKI< 1.5每千条指令的分支预测失败次数

优化报告


维度内容


核心瓶颈嵌套分支的控制流开销


一句话思路分值只有 0–100 —— 那就把 101 种结果预先算好。


报告摘要预计算 lut[256]，把 5 层 if/else 压缩成热循环中的一次字节查表 total += lut[scores[i]]。建表成本 O(101)，被 2000 万次查表完全摊薄。





瓶颈定位
基线每元素要顺序测试最多 5 个条件，产生最多 5 次分支；实际平均约 3 次。
2000 万次元素处理 × 约 3 次分支 = 约 6000 万次分支判断，即便每次只有少量误预测，累积代价也很可观。
更关键的是：这些分支的结果只取决于 101 种可能的分数，完全是在反复计算同样的答案。
优化思路
识别"小值域 + 重复计算"这一模式：输入只有 101 种取值，输出也只有 5 种权重。
预计算 lut[s] 把「分数 → 权重」的映射固化成一次内存查表。
热循环于是退化为 total += lut[scores[i]] —— 无分支、无复杂控制流。
关键改动
建表循环保留原来的 if/else 逻辑（只执行 101 次，写法无需优化）。
unsigned char lut[256]：256 字节稳稳驻留 L1 的一角，查表几乎永远命中。
热循环内删除全部条件判断。
为什么更快
分支数量从平均每元素约 3 次降到 0，Branch MPKI 大幅下降。
每元素的指令数从约 6–10 条降到约 3 条（取字节、零扩展、查表、加），前端压力骤减。
查表只有 256 字节，完全驻留 L1，访存延迟可忽略；建表开销 101 次相对 2000 万次完全可忽略。
常见误区
表开得过大：若值域是 32 位整数就不能直接建表，需要改成分段查表或哈希 —— 本题能建表的前提是"分数 ∈ [0,100]"。
忽略初始化：lut 必须初始化（参考实现用 = {0}），且只填了 0..100；若输入可能超出该范围则需填满 256 项。
在只遍历一轮时照搬：建表的收益来自被大量重复调用摊薄；只跑一轮时收益为负。



要点速记
  • 识别小值域 + 重复计算模式
  • 256 字节表常驻 L1
  • 建表成本被 200 轮摊薄


常见误区与边界条件
  • 值域过大时查表不适用
  • 表必须完整初始化
