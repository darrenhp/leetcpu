不规则聚集：为随机访问提前预取

索引流是顺序的、数据流是随机的 —— 那就用前者去预取后者。

原始英文标题：Irregular Gather — Prefetch Ahead of Random Access

题面

需要按一个索引置换定义的随机顺序，对 128K 个整数求和。基线顺序遍历 indices[]，并按需取 data[indices[i]]。

由于每个索引随机指向 512KB 数据数组中的某个位置，每次迭代都会触发一次 L1 失效 —— CPU 在算出下一个地址之前只能干等。

请加入软件预取提示，让 CPU 提前为后面的迭代发起数据请求。

任务
实现 long solve(const int *data, const int *indices, int n)，返回所有 data[indices[i]] 之和，并使用 __builtin_prefetch 隐藏随机访存延迟。

约束

  • n = 131072（128K，固定）
  • indices[] 是 0..n-1 的一个置换 —— 每个元素恰好访问一次
  • 允许且需要使用 __builtin_prefetch 才能达标
  • 不允许多线程
  • 不允许 SIMD intrinsics
  • 结果必须精确

示例

输入data = 512KB int 数组；indices = 128K 个随机下标
输出所有被引用元素之和
说明关键洞察：indices[] 本身是顺序访问的、缓存友好的，因此可以用它提前知道未来要访问哪些 data 地址。

优化报告


维度内容


核心瓶颈随机访存延迟串行化


一句话思路索引流是顺序的、数据流是随机的 —— 那就用前者去预取后者。


报告摘要利用索引流的顺序性为数据流做预取：在第 i 次迭代就读取 indices[i+24]（顺序、几乎必然命中缓存），并据此预取 data[indices[i+24]]，把串行等待变成提前发起。





瓶颈定位
sum += data[indices[i]] 中，数据地址依赖 indices[i]，而 indices[i] 本身是顺序读的（缓存友好）；真正的失效全部发生在 data 侧。
每次数据访问都是一次串行 L1 失效：必须等当前值返回、累加完成后，下一次迭代才能发起新请求。
指标特征：L1D 平均失效延迟极高（可达数十周期），IPC 很低。
优化思路
随机访问是硬件 stride 预取器的盲区，只能靠软件预取。
由于 indices 是顺序的，读取 indices[i + D] 几乎不会引入额外失效 —— 这是一笔"免费"的先知信息。
提前 D 次迭代发起预取，使得真正需要该数据时它已在缓存中；同时保持 D 个请求在飞行中。
关键改动
if (i + PREFETCH_DIST < n) __builtin_prefetch(&data[indices[i + PREFETCH_DIST]], 0, 1);
参数含义：0 表示读预取，1 表示高时间局部性（尽量留在各级缓存）。
本题 PREFETCH_DIST = 24。
为什么更快
任意时刻有约 24 个数据请求在飞行中，把 200 周期的延迟摊薄到 24 个请求上。
代价是额外的索引读取，但 indices 顺序访问、缓存命中率接近 100%，几乎不增加访存压力。
预取距离需要匹配"每次迭代耗时 × 内存延迟"：D 太小来不及，D 太大预取的数据会在用到前被淘汰。
常见误区
预取距离照抄 24：换成更大数组或更慢内存后，最优值会变化，必须实测扫描。
忘记边界检查：i + D 越界会读取 indices 尾部之外，产生越界访问。
以为预取能减少失效次数：它只让失效重叠，MPKI 不变，变的是平均失效延迟。



要点速记
  • 用顺序的索引流预取随机的数据流
  • 预取距离需实测
  • 关注平均失效延迟而非 MPKI


常见误区与边界条件
  • 越界访问风险
  • 预取距离与环境强相关
